## 6. 为什么“老是不成功”：根因（有日志证据）

### 6.1 第一根因：号池是注销/复用卡，Telegram 只发站内信

典型 IQ 任务 `1755b31f`（+9647706110421，batch `ccde4336`）完整链路：

1. 自建代理匹配成功，但出口是 **哥伦比亚 Bogotá**（目标却是伊拉克）。
2. Grizzly 租号成功（act_id=579701238）。
3. **预检判定白号**：“号码在 Telegram 官方库中未注册”。
4. REGHelp 签发 Push Token 成功（本任务计费 1.0，REGHelp 余额 357.5）。
5. 自建 `api_id=35762565`，MTProto 握手、GetNearestDc、AppConfig 全部成功。
6. `auth.sendCode` 返回：`type=SentCodeTypeApp next_type=None timeout=None`。
7. 流水线正确快失败，避免空等 120 秒。

这证明：

- 设备指纹、Attestation、自定义 API、代理连通 **都不是失败点**。
- 预检“白号”**不能**识别“曾经注册过、现已注销/卸载客户端”的号。对这类号，`contacts` 查询像未注册，`sendCode` 却仍把验证码打到旧设备。
- 短信平台物理上收不到站内信。再跑 200 次也不会凭空变成 SMS。

伊拉克 20/20 都是这条路径。菲律宾租到的 12/12 也是。

### 6.2 第二根因：封禁号占比高，且会继续扣费

28 次 `PHONE_NUMBER_BANNED`。本地封禁缓存从测试前 7 条涨到 35 条（本窗口新确认约 28 个），国家画像变成 ID 11 / CL 10 / BR 4 / KE 3。  
这些号预检往往也过了，钱已经扣，再 cancel 又容易 `EARLY_CANCEL_DENIED`。

### 6.3 第三根因：过早退号被平台拒绝 → 余额塌缩 → 后半场变成 NO_BALANCE

116 次租号里 92 次立刻退号失败（79%）。10 线程把余额从 18.49 打到不够同时锁 10 张廉价卡，于是后 8 轮出现 71 次 `NO_BALANCE`。  
这不是“平台没货”，是 **资金被旧号占用后的并发锁号失败**。延迟退款会回来，但回笼速度赶不上 10 线程消耗。

### 6.4 第四根因：库存 API 不可信

KZ：价格接口显示 11 万库存，10 次 `getNumber` 全空。PK 也有 3 次无号。调度器若只看 `available-countries` 会误判“有货国家”。

### 6.5 第五根因：出口拓扑与目标国不一致（加重风险，但不是本轮主因）

注册通道全部打到 `res.proxy-seller.com` 哥伦比亚出口（日志：`国家=CO 城市=Bogotá`），而目标是 IQ/ID/BR/CL/PH/PK/KE。  
本轮 0 次 `FLOOD_WAIT` / `RECAPTCHA` / 网络超时，所以代理 **没有挡住握手**；但它会让 Telegram 更容易把请求和虚拟号农场关联。要提高短信通道概率，出口必须和号码国家一致。这是下一阶段优化，不是这次 0% 的主因。

### 6.6 本轮明确排除的原因

| 怀疑 | 证据 | 结论 |
| --- | --- | --- |
| 接码没货 | IQ/ID/BR/CL/PH 都能租到号 | 不是主因 |
| Push Token / REGHelp 挂了 | 样本任务 6 秒内拿到 token | 排除 |
| 公开 api_id FLOOD | 强制自建 35762565，0 次 PUBLISHED_FLOOD | 排除 |
| 代理连不上 | 200 次 0 网络超时 | 排除 |
| 验证码输错 / 没收到短信 | 从未进入 SMS 轮询 | 排除 |
| 并发把 Telegram 打爆 | 0 次 FLOOD_WAIT | 排除 |
| 预检把白号误杀 | 本 200 次预检拦截 = 0 | 相反：预检太“宽” |

`/api/sessions` 里出现大量 `node_ke_*.session` / `node_id_*.session` 新文件，那是 Telethon **握手阶段就落盘的空 session**，不是注册成功。判断出号只能看任务 `status=success`：本次为 0。

## 8. 如何把注册成功率拉到最高（按本数据排序）

1. **立刻从轮盘剔除 IQ，以及任何“租号后 APP 率 > 60%”的国家**（本轮 IQ 100%，PH 100%）。继续 10 线程打这些池子只会加速烧余额。
2. **不要用 `getPrices` 库存当可租信号**。KZ 已经证伪。下单前必须用真实 `getNumber` 探测，失败则换国。
3. **把“sendCode 通道 = SMS”做成硬门禁**：`SentCodeTypeApp && next_type is None` 直接弃号；统计 APP 率，超过阈值自动熔断该国。现在流水线已经快失败，缺的是国家级熔断，避免同一国连打 20–50 次。
4. **预检必须保留，但要承认它只能挡住“仍在线的注册号”**。对注销号/卸载号它会放行。要降低假白号，需要：更严的号龄/SKU（平台“新卡”）、多会话交叉探测、以及 sendCode 通道反馈闭环。
5. **代理必须按目标国绑定，禁止全球 CO 出口打全地球**。本轮没被网络错误打死，但地理不一致会继续把号推向 App/封禁桶。
6. **并发降到 3–5，并为 10 张卡预留余额**。公式：`可用余额 >= 单价 × 并发 × 1.2`。低于阈值不要提交 count=10。本轮后半场 71 次 NO_BALANCE 全是违反这条。
7. **退号策略**：命中 APP/BANNED 后不要在 0 秒 cancel。平台明确 `EARLY_CANCEL_DENIED` 时，改为等待可退窗口再 status=8；否则账面余额塌缩，延迟退款也救不了当轮并发。
8. **换号源或换 SKU，不要换线程数**。116 个已租号的短信到达率是 0%。在同一 Grizzly 公开 tg 号池上把 10 线程加到 20 线程，只会更快花光钱。需要“非重号/新卡”产品，或另一个实际走 SMS 的国家/供应商。
9. **成功路径检查清单（本轮全部满足前 5 项，卡在第 6 项）**：  
   有货 → 租到号 → 预检未注册 → Push Token → MTProto 通 → **`sendCode.type` 必须是 SMS** → 收到码 → 落盘。  
   第 6 步 116/116 失败，所以成功率为 0。

## 9. 一句话结论

**老是不成功，不是因为 10 线程不够或系统没跑通，而是当前 Grizzly 热门号池（尤其 IQ，以及 ID/CL/BR/PH/KE）提供的几乎全是 Telegram 眼里的旧号/封禁号：验证码只走站内信或直接拒号；预检查不出注销号；立刻退号又被平台拒绝，余额被锁死。**  
在换掉号源/国家并加上 APP 率熔断之前，继续堆 200 次尝试不会提高成功率，只会重复消耗接码费。
